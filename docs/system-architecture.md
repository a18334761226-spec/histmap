# 系统架构 · 从一句问题到一张地图

> 用户要求两件事：
> ① 有输入图片的地方，根据图片提取风格
> ② 根据用户问题自动获取信息源（二十四史 / 古罗马 / 二战 是不同来源）
>
> 这份文档定义这两块怎么落地，以及**哪些部分必须由代码负责、哪些可以交给模型**。

## 0. 总览

```
        用户问题（自然语言）
   「唐宪宗二年的军阀格局图」
                │
                ▼
  ① 意图解析  ── 把中文史料/问题结构化成查询，**这里用 LLM 是正确的**
                │     输出：{题材, 年代区间, 空间范围, 粒度, 表现意图}
                ▼
  ② 数据源路由 ── topic → adapter 注册表（本文件第 2 节）
                │
                ▼
  ③ 适配器取数 ── 二十四史 / 古罗马 / 二战 各有自己的取数逻辑
                │     统一吐成契约：Region / Frame / Series
                ▼
  ④ 控制层叠加 ── 主权 ≠ 实际控制；事件式时间线支持任意日期
                │
                ▼
  ⑤ 渲染引擎   ── 投影 / 标注避让 / 图例 / 版面（样式外置）
                │
                ▼
  ⑥ 风格层     ── 预设风格 或 从用户上传的参考图提取（本文件第 3 节）
                │
                ▼
           成图 / 成片
```

**贯穿始终的一条铁律**：
> 信息（边界、控制关系、文字、图例）由**代码**负责，一个像素都不能错。
> 模型只用在两个位置：**把非结构化史料变成结构化数据**（①）
> 和**生成不含信息的材质**（⑥ 的一部分）。

---

## 1. 意图解析：什么时候该用模型

| 该用模型 | 不该用模型 |
|---|---|
| 「唐宪宗二年」→ `{dynasty:唐, reign:宪宗, year:807}` | 画边界 |
| 「军阀格局」→ `{layer: control, granularity: 藩镇}` | 决定颜色 |
| 「安史之乱后的河北」→ `{era: 763-, region: 河北三镇}` | 画文字 |
| 从《新唐书·方镇表》抽取藩镇沿革 | 组版式 |

输出的结构化查询就是 `scene.json` 的雏形：

```jsonc
{
  "topic": "tang-fanzhen",          // → 决定用哪个适配器
  "when":  { "from": "807-01-01", "to": "807-12-31" },
  "where": { "bbox": [104, 20, 122, 42] },
  "layer": "control",               // sovereign | control | terrain
  "granularity": "fanzhen",
  "intent": "短视频-横向16:9-宣纸风格"
}
```

## 2. 数据源路由：注册表 + 能力声明

每个适配器自带 manifest（已有实现，见 `packages/core/histmap_core/datasets/base.py`），
路由就是「按 topic 与年代问谁能覆盖，再看几何质量够不够」。

| 题材 | 数据源 | 类型 | 几何质量 | 现状 |
|---|---|---|---|---|
| **二战 / 近现代** | CShapes 2.0 (1886–2019) | A 现成多边形 | 真实率 59.8% | ✅ 已跑通 |
| **宏观索引 / 事件** | AtlasPI (1038 政权, 6500 年) | A 但质量差 | 真实率 19.8%（1250 年仅 4.7%） | ⚠️ 只能做事件与人物索引，**不可做边界** |
| **古罗马** | Pleiades / DARMC / ORBIS | A + B | 待评 | ⛔ 未接入 |
| **二十四史（中国断代）** | **无现成边界源** | **C 史料构建** | — | ⛔ **最大缺口** |
| 世界古代 | OpenHistoricalMap | A | 待评 | ⛔ 未接入 |

### 三类数据形态（这决定了成本）

- **A 现成多边形**：直接取用。近现代、部分古代。成本最低。
- **B 现成点位**：只有城市/据点坐标，需要**建 Voronoi** 才能得到面。古罗马常用。
- **C 史料构建**：从文字史料里抽实体与沿革，自己造几何。**中国断代史属于这一类，也是最贵的。**

⚠️ 路由必须带**质量闸门**：AtlasPI 有 6500 年覆盖、1038 个政权，看起来什么都能答，
但它的几何是 33 顶点的圆饼。**「能返回数据」不等于「能出图」**——
路由前先跑 `quality.py`，不达标的源要降级为「仅事件索引」。

## 3. 风格层：两条路，各自适用

### 3.1 预设风格（已在用）

`src/postfx.py` 的 `atlas / vintage / ink / modern` 四档 + 明暗主题（`dark` / `light`）。
纯代码、确定性、可复现。

### 3.2 参考图提取（`src/style_from_image.py`，已实现）

用户上传一张图 → 量出可复用的风格参数：

| 提取项 | 方法 | 可迁移性 |
|---|---|---|
| 白平衡 | 三通道均值比 | ✅ 高 |
| 明暗分布 | 亮度分位数曲线 | ⚠️ 见下方警告 |
| 平均饱和度 | HSV 的 S 均值 | ✅ 高 |
| 纸纹（低频） | 重度模糊后的亮度起伏 | ✅ 中 |
| 颗粒（高频） | 原图减模糊的标准差 | ✅ 高 |
| 暗角 | 四角亮度 / 中心亮度 | ✅ 高 |
| 主色 | 中位切分量化 | ⚠️ 需多样性检查 |

### ⚠️ 实测踩到的两个坑（都已修，记录在此）

**坑 1：色调迁移对「分类色图像」是错的。**
初版把底图亮度直方图匹配到参考图，结果德国/苏联/英国**全变成一样的米色**、
海洋和陆地一起变亮，信息彻底没了——**和图像模型犯的是同一个错**。
根因：地图的明暗是有语义的（暗=海洋、中亮=陆地、白=文字），
而羊皮纸参考图的明暗只是材质。把前者硬套到后者上等于语义反转。
→ **色调迁移默认关闭。**

**坑 2：参考图只有一个色系时，不能用它的配色。**
羊皮纸类参考图的色相多样性检测出来是 0.000（全是暖黄）。
强行 adopt_palette 会把所有区域压成同一片米色。
→ 新增 `palette_variety()`，**低于 0.18 自动关闭配色替换，只取质感**。

修复后：NCC **0.9948**、色块保真 **100%**、闸门通过——**安全，但效果偏弱**。

### 3.3 诚实的结论：能从图里提取的，比想象中少

参考图最打动人的那些特质——**雕版刻线、手绘轮廓、装饰边框、纸张纤维的细节**——
是**结构性的**，不是色调统计量。色调/纹理统计能迁移的是「配色和氛围」，
迁移不了「画法」。

所以「根据图片提取风格」这条路，真实能力边界是：

- ✅ **能做**：把参考图的**色调、暖冷、饱和度、颗粒、暗角**搬到地图上 → 像做了一层调色
- ❌ **做不到**：用代码复刻参考图的**线条画法**

**补上这个缺口的正确做法**（下一步）：
```
用户参考图 ──(量出风格参数)──> 风格 profile
                                   │
                                   ├─> 参数化描述：「做旧羊皮纸，暖黄，粗颗粒，四角磨损」
                                   │        │
                                   │        ▼
                                   │   让模型生成一张**空白材质图**（无文字无图案）
                                   │        │   ← 模型在这里只做材质，零内容风险
                                   │        ▼
                                   └──> 代码把材质叠到准确底图上
```
这样得到**参考图的画法 + 代码的准确**，而模型全程碰不到「信息」。

## 4. 落地顺序（按依赖关系，不并行）

| 阶段 | 内容 | 为什么这个顺序 |
|---|---|---|
| **P0** | 质感层接进出片管线 | 立刻能出可发布的成片 |
| **P1** | 模型生成空白材质 → 代码叠加 | 补上「画法」缺口，零内容风险 |
| **P2** | 意图解析（LLM → scene.json） | 需要先有多个适配器才有路由价值 |
| **P3** | 二十四史适配器（史料构建） | 最大缺口，也最贵 |
| **P4** | 古罗马适配器（Pleiades + Voronoi） | 验证 B 类（点位→面）的通用性 |
| **P5** | 意图解析 → 路由 → 适配器 全链路 | 前面都通了才有意义 |

**P3 是真正的门槛**：二十四史没有现成边界数据，必须从《新唐书·方镇表》这类
史料构建。早期已经做过一版（`src/parse_fangzhen.py`，42 列 / 1188 行 / 608 条沿革，
807 年得到 37 藩镇 / 262 州），但**还没接进新引擎**，也没有古罗马那样的点位数据可用。
